# spark-images

[![publish](https://github.com/sdaberdaku/spark-images/actions/workflows/publish.yml/badge.svg)](https://github.com/sdaberdaku/spark-images/actions/workflows/publish.yml)

Apache Spark images with Python, pandas and pyarrow, published to `ghcr.io/sdaberdaku/spark`. They are meant as a drop-in replacement for the stock `spark` image wherever it runs: locally with Docker, on Kubernetes, as a Spark Connect server or in a standalone cluster. The stock entrypoint and decommission script are kept, so anything that works with the stock image works here.

The final stage is the official `python:<python>-slim` image. A JRE is copied from `eclipse-temurin:<java>-jre-jammy`, and `/opt/spark`, `/opt/entrypoint.sh` and `/opt/decom.sh` are copied from the stock `spark:<spark>-scala<scala>-java<java>-ubuntu` image. pandas and pyarrow are installed with pip. Spark runs as user `spark` (uid 185).

## Tags

Each image has three tags: `<spark>-python<minor>` (for example `4.2.0-python3.14`, which follows the latest build of that Python line), `<spark>-python<full>` (`4.2.0-python3.14.10`, a pinned Python patch version) and `<major.minor>-python<minor>` (`4.2-python3.14`, which follows the latest Spark patch release).

## Usage

Locally with Docker:

```bash
docker run --rm -v "$PWD/job.py:/tmp/job.py:ro" ghcr.io/sdaberdaku/spark:4.2-python3.14 \
  /opt/spark/bin/spark-submit --master 'local[2]' /tmp/job.py
```

Spark on Kubernetes, with the image used for both driver and executors. The job file is baked into the image, so build an image `FROM` this one that copies `job.py` to `/opt/spark/work-dir/`:

```bash
spark-submit \
  --master k8s://https://<api-server> \
  --deploy-mode cluster \
  --conf spark.kubernetes.container.image=ghcr.io/sdaberdaku/spark:4.2-python3.14 \
  local:///opt/spark/work-dir/job.py
```

Spark Connect server (Spark 4.x, default port 15002):

```bash
docker run --rm -p 15002:15002 -e SPARK_NO_DAEMONIZE=1 ghcr.io/sdaberdaku/spark:4.2-python3.14 \
  /opt/spark/sbin/start-connect-server.sh
```

Spark 4 images bundle the Connect server in the main distribution. On 3.5 add `--packages org.apache.spark:spark-connect_2.12:<spark version>`. `SPARK_NO_DAEMONIZE=1` keeps the start script in the foreground so the container stays up.

Standalone cluster:

```bash
docker run -d --name master --network host ghcr.io/sdaberdaku/spark:4.2-python3.14 \
  /opt/spark/bin/spark-class org.apache.spark.deploy.master.Master
docker run -d --network host ghcr.io/sdaberdaku/spark:4.2-python3.14 \
  /opt/spark/bin/spark-class org.apache.spark.deploy.worker.Worker spark://localhost:7077
```

## Differences from the stock image

- The base is Debian slim from the official `python` image instead of Ubuntu.
- It contains a JRE instead of a JDK.
- Python lives in `/usr/local`, and `PYSPARK_PYTHON` points to it.
- `curl` is kept so that derived images can download jars.
- `wget` and `gnupg2` (the stock build uses them to download and verify the Spark tarball), `net-tools` (debugging only) and `krb5-user` (`kinit` and `klist`; Spark logs in to Kerberos through the JVM with `spark.kerberos.keytab` and `spark.kerberos.principal`) are not installed. A derived image can install them.
- `su` is restricted to the `wheel` group with `pam_wheel`, as in the stock image.

## Size

Measured on 2026-10-27 against the stock `spark:4.2.0-python3` image (Python 3.10) and `ghcr.io/sdaberdaku/spark:4.2.0-python3.14`. Compressed sizes are the sums of the layer sizes in each registry manifest. On-disk sizes come from `docker pull` followed by `docker image inspect -f '{{.Size}}'` on amd64.

| Image | Compressed amd64 | Compressed arm64 | On disk (amd64) |
| ----- | ---------------- | ---------------- | --------------- |
| `spark:4.2.0-python3` | 802 MB | 794 MB | 2.17 GB |
| `ghcr.io/sdaberdaku/spark:4.2.0-python3.14` | 643 MB | 638 MB | 1.76 GB |

The difference comes from the JRE instead of the full JDK, the Debian slim base, Python packages installed without bytecode, and the missing `krb5-user`, `net-tools`, `wget` and `gnupg2`. Our image also carries pandas and pyarrow (about 320 MB on disk), which the stock image does not have.

## Extending with jars

```dockerfile
FROM ghcr.io/sdaberdaku/spark:4.2-python3.14
USER root
RUN curl -fsSL -o /opt/spark/jars/postgresql-42.7.4.jar \
      https://repo1.maven.org/maven2/org/postgresql/postgresql/42.7.4/postgresql-42.7.4.jar \
 && chown spark:spark /opt/spark/jars/postgresql-42.7.4.jar
USER spark
```

The `spark` user owns `/opt/spark`, so the download runs as root and the file is handed back to `spark`. `ADD --chown=spark:spark <url> /opt/spark/jars/` also works.

## Rebuilds

Everything that goes into an image is pinned: the Spark version and the Python patch version in `images.json`, and pandas and pyarrow in `requirements.txt`. Images are rebuilt when a Renovate pull request bumps one of them. Renovate proposes Spark and Python patch updates per row. Tags always point to the latest build. Every row is smoke-tested before it is pushed, so a row that fails the test keeps its previous image.

New Spark minor and major lines, and new Python lines, are discovered daily by the Discover workflow, which compares Docker Hub with `images.json` and opens a pull request on a `discover/<yyyymmdd>` branch with the commit `feat(images): add <additions>`. The pull request renders the README table and merges itself once every row passes the smoke test. A row whose Python versions are not all supported by that Spark line needs a hand edit before the merge.

OS-level fixes that do not change a tag (a new Debian package build, for example) are not picked up until the next rebuild. That gap is accepted.

Tags are never deleted. A rebuild moves the tag to the new image, and the old image becomes an untagged version that the cleanup removes once it is 30 days old. The Publish workflow runs the cleanup after each publish, and can run it alone from the Actions tab (inputs `only_cleanup` and `cleanup_dry_run`). For a reproducible pin use the image digest (`ghcr.io/sdaberdaku/spark@sha256:...`), which Renovate can also keep updated. A digest pin stays pullable for at least 30 days after its tag moves, so bump the pin within that time. Publishing runs only when a change touches the Dockerfile, `images.json`, `requirements.txt`, `test/` or the publish workflow, so unrelated merges leave existing digests alone.

## Development

`renovate.json` configures Renovate. The Mend Renovate app must be installed on the repository for the configuration to act. Non-major updates (Spark and Python patches, GitHub Actions, pandas and pyarrow) arrive as one weekly pull request, which merges itself once `ci-ok` passes.

The CI `checks` job runs all unit tests and fails when the tag table does not match `images.json`. Render it with `python scripts/render_readme.py` and run the unit tests with `python -m unittest discover -s tests`.

### Adding a row

Add a Spark version, or a full Python version (for example `3.14.10`), in `images.json`, then render the README table.

### Running the smoke test locally

```bash
docker build --build-arg SPARK_VERSION=4.2.0 --build-arg SCALA_VERSION=2.13 \
  --build-arg JAVA_VERSION=21 --build-arg PYTHON_VERSION=3.14.10 -t spark-local:4.2.0-python3.14 .
bash test/smoke.sh spark-local:4.2.0-python3.14 3.14.10
```

The CI `build` job runs every row on amd64 and arm64. The smoke test checks the uid, the Python version, a Spark SQL job, an Arrow conversion, an RDD job with a Python lambda, the pandas and pyarrow imports and the stock entrypoint.
