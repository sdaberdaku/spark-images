# spark-images

[![publish](https://github.com/sdaberdaku/spark-images/actions/workflows/publish.yml/badge.svg)](https://github.com/sdaberdaku/spark-images/actions/workflows/publish.yml)

Apache Spark images with Python, pandas and pyarrow, published to `ghcr.io/sdaberdaku/spark`. They are meant as a drop-in replacement for the stock `spark` image wherever it runs: locally with Docker, on Kubernetes, as a Spark Connect server or in a standalone cluster. The stock entrypoint and decommission script are kept, so anything that works with the stock image works here.

The final stage is the official `python:<python>-slim` image. A JRE is copied from `eclipse-temurin:<java>-jre-jammy`, and `/opt/spark`, `/opt/entrypoint.sh` and `/opt/decom.sh` are copied from the stock `spark:<spark>-scala<scala>-java<java>-ubuntu` image. pandas and pyarrow are installed with pip. Spark runs as user `spark` (uid 185).

## Tags

Each image has four tags: `<spark>-python<minor>` (for example `4.2.0-python3.14`, which follows the latest build of that Python line), `<spark>-python<full>` (`4.2.0-python3.14.10`, a pinned Python patch version), `<major.minor>-python<minor>` (`4.2-python3.14`, which follows the latest Spark patch release) and the dated tag described under Rebuilds.

Spark 3.5.9 with Python 3.12 is not published. PySpark 3.5 imports `distutils`, which Python 3.12 removed, so `createDataFrame` from pandas fails (checked with `test/smoke.sh`).

```bash
docker pull ghcr.io/sdaberdaku/spark:4.2.0-python3.14
```

## Usage

Locally with Docker:

```bash
docker run --rm -v "$PWD/job.py:/tmp/job.py:ro" ghcr.io/sdaberdaku/spark:4.2.0-python3.14 \
  /opt/spark/bin/spark-submit --master 'local[2]' /tmp/job.py
```

Spark on Kubernetes, with the image used for both driver and executors. The job file is baked into the image, so build an image `FROM` this one that copies `job.py` to `/opt/spark/work-dir/`:

```bash
spark-submit \
  --master k8s://https://<api-server> \
  --deploy-mode cluster \
  --conf spark.kubernetes.container.image=ghcr.io/sdaberdaku/spark:4.2.0-python3.14 \
  local:///opt/spark/work-dir/job.py
```

Spark Connect server (Spark 4.x, default port 15002):

```bash
docker run --rm -p 15002:15002 -e SPARK_NO_DAEMONIZE=1 ghcr.io/sdaberdaku/spark:4.2.0-python3.14 \
  /opt/spark/sbin/start-connect-server.sh
```

Spark 4 images bundle the Connect server in the main distribution. On 3.5 add `--packages org.apache.spark:spark-connect_2.12:3.5.9`. `SPARK_NO_DAEMONIZE=1` keeps the start script in the foreground so the container stays up.

Standalone cluster:

```bash
docker run -d --name master --network host ghcr.io/sdaberdaku/spark:4.2.0-python3.14 \
  /opt/spark/bin/spark-class org.apache.spark.deploy.master.Master
docker run -d --network host ghcr.io/sdaberdaku/spark:4.2.0-python3.14 \
  /opt/spark/bin/spark-class org.apache.spark.deploy.worker.Worker spark://localhost:7077
```

## Differences from the stock image

- The base is Debian slim from the official `python` image instead of Ubuntu.
- It contains a JRE instead of a JDK.
- Python lives in `/usr/local`, and `PYSPARK_PYTHON` points to it.
- `krb5-user`, `net-tools`, `wget` and `gnupg2` are not installed.

## Size

Measured on 2026-10-27 against the stock `spark:4.2.0-python3` image (Python 3.10) and `ghcr.io/sdaberdaku/spark:4.2.0-python3.14`. Compressed sizes are the sums of the layer sizes in each registry manifest. On-disk sizes come from `docker pull` followed by `docker image inspect -f '{{.Size}}'` on amd64.

| Image | Compressed amd64 | Compressed arm64 | On disk (amd64) |
| ----- | ---------------- | ---------------- | --------------- |
| `spark:4.2.0-python3` | 802 MB | 794 MB | 2.17 GB |
| `ghcr.io/sdaberdaku/spark:4.2.0-python3.14` | 643 MB | 638 MB | 1.76 GB |

The difference comes from the JRE instead of the full JDK, the Debian slim base, Python packages installed without bytecode, and the missing `krb5-user`, `net-tools`, `wget` and `gnupg2`. Our image also carries pandas and pyarrow (about 320 MB on disk), which the stock image does not have.

## Extending with jars

```dockerfile
FROM ghcr.io/sdaberdaku/spark:4.2.0-python3.14
ADD https://repo1.maven.org/maven2/org/example/lib/1.0/lib-1.0.jar /opt/spark/jars/
```

The `spark` user owns `/opt/spark`. If you use `ADD` with a URL, add `--chown=spark:spark` or switch to `USER root` for the step.

## Rebuilds and dated tags

Everything that goes into an image is pinned: the Spark version and the Python patch version in `images.json`, and pandas and pyarrow in `requirements.txt`. Images are rebuilt when a Renovate pull request bumps one of them. Renovate proposes patch updates per row; a new Spark or Python minor is added by hand as a new row. Each rebuild also gets a dated tag of the form `<spark>-python<minor>-<YYYYMMDD>`. The undated tags always point to the latest build. Every row is smoke-tested before it is pushed, so a row that fails the test keeps its previous image.

OS-level fixes that do not change a tag (a new Debian package build, for example) are not picked up until the next rebuild. That gap is accepted.

Floating tags (`<spark>-python<minor>`, `<spark>-python<full>` and `<major.minor>-python<minor>`) are never deleted. Dated tags are kept for 90 days. Untagged versions are removed once nothing references them. The Publish workflow runs the cleanup after each publish, and can run it alone from the Actions tab (inputs `only_cleanup`, `cleanup_dry_run` and `cleanup_older_than`).

## Development

`renovate.json` configures Renovate. The Mend Renovate app must be installed on the repository for the configuration to act. Patch updates, GitHub Actions updates and minor or patch updates of pandas and pyarrow are merged automatically once `ci-ok` passes.

The CI `readme` job regenerates the tag table. When a pull request leaves it stale, the job commits the new table to the pull request branch and fails once; the run started by that push passes. To render it yourself:

```bash
python scripts/render_readme.py
python -m unittest tests/test_render_readme.py
```
